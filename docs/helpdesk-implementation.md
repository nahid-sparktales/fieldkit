# Help-desk priorities 2–5 implementation record

## Plan and repository map

The implementation extends the existing Node/React application, PostgreSQL transactions and pg-boss jobs. Priority 1 and live-provider verification are excluded. No production migrations, DNS/vendor changes, deployment, or real customer mail are part of this work.

1. **Shared authorization (schema 19):** `packages/platform/src/permissions.ts`, `permissions-schema.ts`, `auth.ts` and `apps/api/server.ts`. Preserve built-in roles, add explicit capabilities and ticket visibility, and establish tenant-scoped team keys for the dependent features.
2. **Email intake (schema 20):** extend `ticket-email.ts`, add durable intake schema/services, reuse scanned attachments and the existing message/outbox machinery; extend `TicketEmailSettings.tsx` and add focused email tests/operator documentation.
3. **Staff productivity (schema 21):** `productivity.ts`, contracts/schema, administration components, `Portal.tsx` and `InboxQueue.tsx`. Forms retain immutable revisions; macro changes commit with the ordinary message transaction; saved queries enforce current visibility.
4. **Human routing (schema 22):** `human-routing.ts`, contracts/schema and team administration. Persist availability, queues and round-robin position. Serialize automatic and manual assignment using a workspace transaction lock before conversation locks.
5. **Staff identity (schema 23):** extend the installed Better Auth library for OIDC and TOTP/recovery, add staff identity policy/role administration and local protocol/security tests. Customer and service authentication remain separate.

Root integration points are `Database.migrate/enqueue/event`, `Platform.newConversation/message/control/workers`, the existing authenticated REST router and the existing staff/portal screens. Individual feature modules own their contracts and validation. Migrations are additive and idempotent; new routing and identity enforcement default off.

Verification uses isolated databases ending in `_test`, synthetic email, injected transports and a local OIDC provider. Concurrent feature tests use separate databases; the existing shared-database regression suites run sequentially. Each priority includes acceptance, rejection/bypass and neighboring-feature checks, followed by typecheck/build and browser verification.

## Architecture and security decisions

- **One ticket system:** email, portal and widget use the existing conversation/message model, timeline, scanned attachment storage, SLA events and notification/workflow pipeline. Email intake defaults to human handling and works without a model. Email-only contacts remain unverified; matching a sender to a staff or portal email grants no authority.
- **Durable effects:** PostgreSQL uniqueness and committed receipt/outbox state deduplicate retries. SMTP remains at-least-once, with explicit handling of uncertain sends; provider acceptance is not represented as delivered. Macro previews have no sending side effects. An explicit send commits its authorized patch and normal message/outbox together or rolls everything back.
- **Assignment concurrency:** workspace routing advisory locks precede conversation/member locks. Automatic claims recheck active authority, team, fresh availability and cross-team total capacity inside the transaction. Availability, routing position, queue age and manual ownership persist across restart. Permission/team changes use the same lock order.
- **Live authorization:** the server refreshes membership, role and team scope for protected requests and direct conversation access. Saved-view rows and counts use the same visibility predicate. Attachments, notes, internal fields, customer history, SSE and actor-owned assistance jobs preserve the boundary. Legacy aggregate/evidence surfaces without row-level filtering deny restricted ticket scopes; transcript-bearing surfaces also require private-note access. Role/member changes revoke affected sessions, including sessions in other workspaces.
- **One authentication system:** OIDC extends Better Auth's existing accounts, sessions and protocol primitives, using the authorization-code flow with state, nonce, PKCE and signed ID-token validation. Linking requires an authenticated, invited member with fresh proof; verified email alone cannot link or provision membership. Provider revision and workspace are bound to each transaction. Access, refresh and ID tokens are not retained.
- **MFA and recovery:** first enrollment requires a valid authenticator code. Pending password and SSO challenges have no usable staff session. Recovery verifiers are one-way hashes and atomically consumed; TOTP replay claims are durable. OIDC secrets and TOTP material use the existing encryption key. Policy enforcement and factor removal serialize around user rows, with a database guard preventing concurrent removal of a required factor. Recovery requires an operator-approved existing owner with local password plus MFA, or the documented offline host/DB recovery command.

### Permission matrix

This table summarizes defaults; `permissions.ts` is the exact allowlist and the Security screen renders it.

| Area                                                                          | Owner | Administrator                 | Agent | Custom roles                                                                                      |
| ----------------------------------------------------------------------------- | ----- | ----------------------------- | ----- | ------------------------------------------------------------------------------------------------- |
| Read/reply/note/update/assign visible tickets; internal fields; customer read | Yes   | Yes                           | Yes   | Explicit capabilities and all/team/assigned scope                                                 |
| Personal macros/views, assistance, permitted attachments                      | Yes   | Yes                           | Yes   | Explicit capabilities                                                                             |
| Fields/forms, shared macros/views, teams/routing, email administration/retry  | Yes   | Yes                           | No    | Explicit capabilities; administrative routing/email operations also require all-ticket visibility |
| Membership invitations/removal/assignment                                     | Yes   | Yes, within delegation limits | No    | `members:manage`, fresh proof and delegation checks                                               |
| Custom-role and identity-policy management                                    | Yes   | No by default                 | No    | `roles:manage` / `identity:manage`, fresh proof and bounded delegation                            |
| Legacy governed-action configuration / credentials                            | Yes   | No                            | No    | Existing owner-only ceiling remains                                                               |

Custom roles replace the built-in capability set. Existing legacy administrator/owner service checks remain an additional ceiling: select the Administrator base role for custom roles needing legacy administrator tools. Unknown capabilities deny access. Role managers cannot modify their own assigned role, exceed their capability/scope boundary, alter their own access, create an owner, or demote/disable an existing owner through ordinary membership APIs. Shared definitions never grant ticket visibility.

## Operator activation, disable and remaining boundaries

1. Back up the database and existing encryption/auth keys, stop application and worker processes, upgrade, and run the normal `npm run migrate`. Restart on the same configured keys. New tables are additive; automatic routing and identity enforcement start off. Existing support integrations retain private-reply behavior, with new-ticket intake initially disabled.
2. Configure SMTP and authenticated Postmark inbound routing for each support address in **Publish → Channels → Email support**. Activate intake, optional acknowledgements/workflows and default teams deliberately. The UI does not provision mailboxes or verify DNS/vendor delivery. See [email setup, health and recovery](helpdesk-email.md).
3. Configure fields/forms, sharing and views in **Productivity**; review dependent forms after field-schema changes. See [forms, macros and views](helpdesk-productivity.md).
4. Add team members, set workload limits and optional overflow, enable team/workspace routing, and have agents select Available. Historical/manual assignments are preserved. See [routing behavior and disable procedure](helpdesk-routing.md).
5. Register the exact OIDC callback at the operator's IdP, configure its write-only secret, invite/link staff, confirm TOTP and save recovery codes. Public issuers require validated HTTPS; private issuers require exact `FIELDKIT_OIDC_ISSUERS` entries. Before enforcement, configure a viable owner in `FIELDKIT_BREAK_GLASS_USERS`. See [SSO/MFA rollout and offline recovery](staff-identity.md), [custom roles](staff-roles.md) and `.env.example`.

Disable features through their settings while retaining historical records. Disable identity enforcement before disabling its provider. Stopping automatic routing does not clear ownership; disabling new email intake preserves existing replies. A destructive down-migration is not a safe rollback; database restoration requires the normal backup/recovery procedure.

**Not run:** production migrations, deployment, live SMTP/Postmark round trips, real enterprise IdP tests, DNS changes or the owner's separate Priority 1 release audit. The local OIDC contract is implemented and verified; environment-specific provider activation remains the operator's responsibility. No unresolved local acceptance blocker is known.

**Outside scope:** SAML/SCIM/group provisioning, outbound binary attachment forwarding, automatically claiming email-only tickets through a portal account, telephony/social channels, workforce scheduling/forecasting, billing/paywalls and full Zendesk parity. Provider delivery/bounce data is only represented when actually available; SMTP acceptance is not proof of delivery.
